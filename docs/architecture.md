# 架构

## 为什么需要这么多层

目标只有一句话：**手机上打开就是我的 DSH**。

但从"手机"到"DSH"之间隔着四道障碍，每一道都需要一层来解：

| 障碍 | 解法 |
|---|---|
| 电脑没有公网 IP | Cloudflare 命名隧道（出站连接，穿透 NAT） |
| 上游只监听回环地址 | 本地反向代理（对外 3080，对内转发） |
| 上游校验请求来源 | 代理改写 `Host` / `Origin` / `Referer` |
| 上游要求会话 cookie | 代理用本机密钥签一个 |

再加两层是为了"用得下去"：守护进程（不然挂了没人管）和移动端壳（不然每次要开浏览器）。

## 三个设计决定

### 1. 为什么代理不直接连 DSH 的端口

DSH 桌面端的端口是**动态的**——每次启动都可能变（每次启动都不同）。

代理不能写死端口，所以：

- 定时扫描本机监听端口，认出哪一个是 DSH 的
- 结果缓存一小段时间（默认 5 分钟）
- 转发时用缓存值

代价是**上游重启后有一段盲区**。后续优化方向：连接被拒时立刻失效缓存并重探一次。

### 2. 为什么守护要"先诊断再动手"

早期版本只要探活失败就重建隧道。问题在于：

- **源站没开**时，隧道重建一百次也没用，只是每次白断一次线
- **代理挂了**时，重建隧道同样无用

所以现在连续失败 2 次后先诊断：

```
源站进程在吗？  否 → 尝试拉起源站
代理端口通吗？  否 → 尝试启动代理
两者都正常     → 这才是隧道层问题，重建隧道
```

只有第三种情况才重建。

### 3. 为什么配置用 JSON 不用 YAML

项目同时有 Node 和 PowerShell 脚本。JSON 两边都能原生解析；YAML 在 PowerShell 里
需要额外模块。配置项又是扁平的，用 YAML 也没有结构优势。

## 数据流：一次手机访问

```
1. 手机 GET https://<domain>/
2. Cloudflare 边缘终止 TLS
3. 隧道把请求转给 cloudflared → 127.0.0.1:3080
4. 代理检查 cookie：
   ├─ 没有 → 返回 401 或跳登录页
   └─ 有   → 继续
5. 改写 Host/Origin/Referer
6. 转发到 127.0.0.1:<上游端口>
7. 上游返回 HTML
8. 代理改写响应头（必要时代码注入 PWA 清单），去掉 content-length 与 transfer-encoding
9. 返回给手机
```

第 8 步那两个头是踩过的坑：改写 HTML 后长度变了，但上游还带着 `transfer-encoding: chunked`，
两个头同时存在会让客户端解析失败。**必须两个都删，只删一个不够。**
